# NOTES

Assumption changes and choices made while building (see PRD working rule 9).

- `ultralytics` is an optional extra (`pip install -e .[yolo]`) so the base install stays light; classical detector works without it.
- `ffmpeg` was not on PATH at scaffold time; needed for #18 (`brew install ffmpeg`).
- Dataset labels are one full-image box per photo (`0 0.5 0.5 1 1`, Beef/Pork), so it is an image classifier in YOLO format. Textures come from random crops, using a black-border mask instead of labels. Issue #16 (precision/recall vs dataset labels) is therefore degenerate; I will report it as "does the model fire on real meat photos" and say so in the report.
- Textures use `train` only and the Pork class only (`textures.classes: [1]`); `valid` and `test` stay untouched for #16. Dataset has 171 source photos x 3 augmented copies.
- Dataset "fat" patches are pale pink; they are tinted toward cream in `TextureBank.sample`. Real lean patches run magenta, so #3 needs a per-piece colour shift toward pork pink.
- Pieces are generated with width <= 0.75 x length so the long axis (and therefore the grasp yaw) is well defined; the PRD ranges allow near-round pieces where no long axis exists. Edge wobble skips the k=2 harmonic because it tilts the principal axis.
- Piece weight is sampled in the PRD 200-400 g range and thickness derived from it (clipped to 15-30 mm), so weight and thickness stay consistent with the area.
- Camera/belt layout: the belt is 600 mm wide and the image is 1280x720, so the camera must see the full belt width across the image columns and ~337 mm of travel down the image rows (`camera.fov_mm` is `[across, along]`). Belt frame -> image is a 90 degree proper rotation (see `sim/geometry.py`); belt y runs right-to-left across the image.
- Fat side is defined relative to the normal of the reduced [0,180) angle. Converting between image and belt frames can wrap that angle and flip the sign; `geometry.fat_side_image_to_belt` is the one place that handles it, and perception (#9) must use the same rule via calibration.
- Cluster arrivals: burst_prob 0.1, size 2-3, spacing [-15, 30] mm. The PRD's 50 +/- 10 pieces per 60 s is about one standard deviation with heavier bursts, so bursts are kept mild by default.
- Camera model: scene is composited in the ideal frame on a canvas with a 100 px margin, then warped once (tilt homography + OpenCV radial distortion, `Camera.project` is the forward model and the remap maps are its inverse). Lens/geometry parameters are drawn once per Camera instance (a real camera is fixed); exposure and white balance drift per frame; noise is drawn per frame. Dataset export (#6) should create several Camera instances to get geometry variety.
- Sprites are drawn at whole pixels; truth polygons are built from the drawn position (sub-pixel outline from a 4x upsampled alpha) so truth matches pixels to <= 2 px (measured max 1.9 px, 0.7% area bias). The exact center stays in `x_mm, y_mm`.
- Render speed on this machine: ~25 ms/frame (~40 fps) at 1280x720, above the 15 fps target. The first frame interval after a Camera is created depends on when it started watching; later intervals are exactly 20 mm.
- `outputs/debug/camera_sample.mp4` is written with OpenCV's mp4v codec because ffmpeg is not installed here; the final demo video (#18) needs ffmpeg for H.264.
- Dataset (#6): 3,400 train / 600 val frames at 640x360 (labels come from the full-res instance map, visible part of each piece), split by scene so no scene is in both. ~18% of frames are empty backgrounds because many scenes are sparse; kept as negatives. Zip is 104 MB. The fixed test set (500 frames, 10 sequences of 50 consecutive frames, exactly 20 mm apart) lives in `outputs/test_set/` with full truth; it uses a denser, burstier line (70/min, burst_prob 0.2) than the demo so touching pieces are common enough to measure. It is not randomized and uses scene seeds disjoint from training.
- Verified locally: Ultralytics 8.4.191 scans all 4,000 images with 0 corrupt / 0 missing / 0 warnings, and every notebook cell runs end to end on CPU (1 epoch, 48 images). Not verified: speed and the full 60-epoch run on a Colab T4.
- Calibration (#7): `perception/calibration.py` sees only images plus what an operator knows (inner-corner pattern 9x6, 25 mm squares, and where a flat board was laid). Intrinsics and distortion come from 14 tilted-board views (a flat board at one tilt cannot fix focal length); the image-to-belt homography comes from 4 flat boards at known belt positions. Distortion model is radial k1, k2 with no tangential term, matching how the sim lens is built; a real lens may need more terms. Flat board convention: the belt (x, y) of its outer top-left corner, board +X along belt -y, board +Y along belt +x.
- Calibration results on simulated boards (3-4 random cameras): RMS 0.03-0.04 px, worst corner error on held-out boards 0.04 mm, worst error over the whole field of view 0.11 mm, focal length within 0.1%. These are sim-clean numbers (analytic edges, mild noise); a real camera and board will not be this good. k2 is only weakly determined (as usual) but does not matter for the mapping.
- Working rule 1 is now a test (`tests/test_isolation.py`): nothing in `perception/` or `control/` may import `meatpick.sim`. The calibration code has no sim imports; the sim side (`sim/calibration_target.py`) renders the boards through the same lens model as the frames. `python -m meatpick calibrate` writes `outputs/calibration.json` and `outputs/debug/calibration.png`.
- Classical detector (#8, `perception/classical.py`): colour distance from the belt's own median Lab colour (so a different belt shade needs no retuning; checked on randomized belts: 100% of 457 isolated, mostly visible pieces found), morphology, hole filling, then a split step for blobs. Split = distance-transform seeds (0.65 of the blob's max) partitioned by colour watershed; if that finds one seed, a fallback cuts along dark edge valleys (rim shading and contact shadow) for overlapping pieces with no waist. Works at half resolution; masks are returned at full resolution. `Detector` / `MaskInstance` in `perception/detector.py` are the interface YOLO (#9) must match.
- Classical results. Fixed test set (run ONCE after tuning on separate dev frames, nothing changed afterwards): recall 96.9% (target >= 95%), precision 99.7%, isolated 100%, touching 95.2% (503 touching piece-frames), mean mask IoU 0.968, 2.25 ms/frame mean and 3.1 ms p95 (budget 15 ms). Honest caveats: the test set holds only 55 distinct pieces (774 is piece-frames; each piece is in view ~14 frames), 51 are found in every frame and 4 are ever missed, and those 4 carry the whole shortfall; per-sequence recall ranges 0.90-1.00. Independent samples of the same line gave lower numbers: dev set 94.4%, fresh dense scenes 83%, and the PRD's nominal 50/min line 88.3% (touching pieces 53.7%, isolated 100%). Treat the true figure as roughly 85-95% with overlapping pieces as the weak spot.
- Known classical failure: a piece lying over another with no dark seam between them (colour step only) is returned as one merged mask, and its confidence stays high (0.9+), so confidence does not flag it. Splitting on colour alone would also cut fat strips off pieces, so I did not add it; the YOLO instance masks (#9) are the intended fix, and #15 reports touching pieces separately.
- Tuning discipline (working rule 8): thresholds were tuned on `outputs/dev_set` (seeds 5000+, regenerate with `python -m meatpick devset`); `outputs/demo_set` (`devset --nominal`) is a second non-test sample at 50/min. Test set evaluated once via `python -m meatpick eval-detector --set outputs/test_set`; reports are in `outputs/reports/`. `eval/matching.py` and `eval/detector_eval.py` (IoU >= 0.5, pieces below 50% visibility neither required nor penalised) are reused by #15. The detector's pixels-per-mm comes from the calibration (#7), not from the sim.
- YOLO + pose (#9): `perception/yolo.py` wraps Ultralytics behind the same `Detector` interface (full-resolution masks via `retina_masks`), `perception/pose.py` turns a mask into a `Detection` in belt mm (centroid, PCA long axis in [0,180), extents, fat side, area-based weight, touching flag within 25 mm), and `perception/factory.py` builds a `Perceiver` that uses YOLO when `models/best.pt` and ultralytics exist and otherwise falls back to the classical detector with a logged warning (work is never blocked on the model). Pose is computed after mapping pixels through the calibration, so it is metric despite lens distortion and tilt.
- Fat side: the two long edges (2-9 mm in from each edge) are compared on paleness = L - chroma (Lab); the paler edge is the fat. Same normal convention as the sim truth ((-sin a, cos a) of the reduced angle).
- Results on the DEV set (not the test set; the official numbers come from #15), pieces >= 95% visible and not touching, 105 scored. Classical masks: centre 0.28 mm median / 0.67 p95 (target < 3 / < 8), angle 0.14 deg / 0.73 (target < 3 / < 8), fat side 100% on isolated pieces (target >= 95%). YOLO masks: centre 0.76 / 1.18 mm, angle 0.18 / 0.59 deg, fat side 100% isolated and 98% on touching pieces. Detection on dev: YOLO recall 100% including all 198 touching piece-frames (classical 94.4%), precision 99.7%, mean mask IoU 0.980, 28.8 ms/frame on this Apple M4 (target < 50 ms; the PRD's 2-core workspace will be slower, not measured). These are in-distribution (same simulator as the training data); real photos are #16.
- Known issue, YOLO centre bias: YOLO masks sit about 1.0 px up and 0.45 px left of the true mask (about 0.6 mm along travel on average), identical whether masks come from the prototype masks or the polygons, so it is in the model. Most likely cause is my label export: `cv2.findContours` returns pixel-centre indices but YOLO reads label coordinates as pixel edges, a half-pixel shift. Not fixed because I cannot verify it without retraining on Colab; fix on the next retrain by adding 0.5 to the contour coordinates in `dataset_export.visible_polygon`, then re-measure. 0.6 mm is inside the 2 mm grasp budget (#11) but uses part of it.
- Limits: estimated weight has a 15% median / 40% p95 error because thickness is assumed (no depth sensing), as the PRD says. YOLO was trained only on blue belts (hue jitter about +-8 degrees); other belt colours are untested for YOLO and should be handled by retraining with wider belt-colour randomization. The classical detector estimates the belt colour per frame and passed tests on green and two blues, but would struggle where the belt resembles the meat (white or pink belt).
- Tools: `python -m meatpick eval-detector --detector {classical,yolo} --set <dir> --pose` (detection + pose accuracy), `poses-debug` (long axis, grasp line, fat arrow overlay; `outputs/debug/poses.jpg`).
- Tracker (#10, `perception/tracker.py`): Hungarian assignment on centre distance (gate 30 mm, +20 for detections cut by the frame edge), exponential centre smoothing, circular median angle, majority fat side, confirmed after 2 hits. Positions are stored at a reference encoder count and dead-reckoned (`x + d_encoder * 0.1 mm`), so tracks keep coasting after leaving the camera view until picked or past the reach zone (the PRD's "delete after leaving the field of view" would drop pieces before the arm at 600-1000 mm, so I did not do that). `update()` returns Track snapshots, not live objects. `Track` has extra defaulted fields (touching, length, width, weight, hits) for the scheduler.
- Four bugs found by a long in-memory run (838 pieces, true positions known) that the 55-piece test set could not show, all fixed with regression tests (each confirmed to fail when the bug is put back): (1) a piece leaving the bottom of the view has a visible centroid up to half its hidden length behind its true centre, which broke the gate and spawned ghost tracks; now association compares against the expected visible centroid and nothing is spawned from detections cut by the exit edge; (2) an entering piece's centroid moves at half belt speed, so tracks that dead-reckoned it drifted off; they now follow the measurement until the first clean view; (3) the tilted camera really sees belt x 17-358 mm, not 0-337.5; the tracker takes the span from `Calibration.view_span_x_mm()`; (4) YOLO masks stop a few pixels short of the frame edge, so "touches the border" uses an 8 px tolerance (`touches_border` in `perception/detector.py`). Before the fixes the median track error at the arm was 14.8 mm; after, 0.81 mm.
- Tracking results. Fixed test set, YOLO, run before and after the fixes (the fixes came from the long run, not from test-set tuning): 55 pieces, 0 ID switches, 0 duplicate tracks, coverage 97%. Long run, dense 70/min line, 838 pieces: ID switches 2 = 1.19 per 500 pieces (target <= 1), 3 pieces with duplicate tracks (target 0); every switch and duplicate was on a partly covered piece (visibility 0.51-0.78). Position error at the arm vs the TRUE centre: uncovered pieces (493) median 0.74 mm, 95.5% within 2 mm; partly covered pieces (337) median 1.0 mm, 69% within 2 mm. A covered piece's visible centroid is not its true centre, so no 2D detector can match the truth there; the tracker reproduces the detection faithfully. Angle error at the arm: median 0.19 deg; fat side 94.8%.
- OPEN items from #10, not resolved: (a) 4% of uncovered pieces (about 20 of 493) are still more than 20 mm off at the arm, cause not found; (b) 34 of 864 pieces reaching the reach zone (4%) had no confirmed track at all; (c) switches/duplicates are slightly above target on overlapping pieces. Carry into #11/#12: the scheduler should skip or down-rank pieces with `touching` set or low confidence, and #17's miss rates will show how much (a) and (b) cost. The long run at the PRD's nominal 50/min was not run.
- Tools: `python -m meatpick eval-tracking --set <dir>` (saved sequences), `--long N` (in-memory run with truth, add `--nominal` for 50/min; takes about 10 min with YOLO), `tracks-debug` (clip with track IDs: `outputs/debug/tracks.mp4`).
- Arm model and intercept (#11, `control/arm_model.py`, `control/intercept.py`; `control/` imports nothing from `sim/`): move time is trapezoidal (accelerate, cruise, brake; too-short moves are triangular), plus a fixed 0.05 s wrist penalty when the wrist turns more than 90 degrees. With the PRD defaults a 400 mm move is exactly 0.4 s, so the PRD cycle is 0.4 + 0.15 + 0.4 + 0.1 = 1.05 s; I placed the bin 400 mm from the pick line (`robot.bin_mm`) and the arm base at the middle of the reach zone (`robot.base_mm`) to match. Positions are in the belt frame (arm fixed in it, like the camera); `InterceptPlan.to_command` converts to the robot frame (belt minus base).
- Intercept: iterates grip time -> piece position -> move time (3 iterations / 1 ms), waits for a piece that has not yet reached the zone, and rejects `too_late`, `outside_reach` or `belt_stopped`. During the 0.15 s grip the arm rides the belt, so it leaves for the bin from the pick point plus belt travel over the grip time. `Arm` is a timestamped state machine (IDLE, MOVING_TO_PICK, GRIPPING, MOVING_TO_BIN, RELEASING); `begin(plan)` schedules a cycle, `advance(now)` fires the "grip", "release", "idle" events. The piece should be removed from the belt at the "grip" event (#14).
- Accepted simplification: the wrist-rotation rule is read literally. Gripper yaw is long axis + 90 reduced to [0, 180) and the wrist turns by the plain difference, so a turn over 90 degrees costs the penalty (`robot.wrist_symmetric: true` lets it take the short way instead, which would make the penalty unreachable for a 180-degree-symmetric gripper). The arm starts with yaw 0.
- Caveat for #13: `plan_intercept` predicts belt travel with the current speed unless it is given a `travel_fn`. A unit test shows a belt that is decelerating at the PRD's 0.5 m/s^2 would put the arm more than 10 mm off with the constant-speed default, so the adaptive belt controller must supply its planned speed profile as `travel_fn`.
- Acceptance (#11): perceiving and tracking a real simulated piece (classical detector, 3 seeds) and comparing the planned pick point with the piece's true position at grip time is within 2 mm (test passes; a deliberately broken planner fails it). Not measured: the same with the YOLO detector or in a busy line; that comes with the closed loop (#14).
